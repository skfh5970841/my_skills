# 채사장 스킬을 단순하게 개선하는 계획

목표는 사용자가 **무엇을 왜 고쳤고, 결과가 어떻게 달라졌는지** 직접 이해하는 것이다. 아래 계획에 이어 문서 끝에 2026-09-09의 optimizer 절차 개선 기록을 남겼다. 글 품질의 향상을 검증한 문서는 아니다.

## 추천 방향

기존 `chaesajang-family-optimizer`의 기본 사용법을 다음 한 흐름으로 줄인다.

**문제 하나 고르기 → 작게 고쳐 비교하기 → 좋아진 변경만 반영하기.**

새 optimizer나 평가 시스템을 만들 필요는 없다. 기존 자동화는 보존하되 일상적인 개선의 필수 절차에서 뺀다. 외부 조사는 판단 근거가 부족할 때만 사용한다.

위의 두 개선 후보는 지침을 읽고 발견한 점이다. 실제 출력에서 문제가 확인됐다는 뜻은 아니다.

## 실제 개선은 이렇게 진행한다

### 1. 문제 하나 고르기

사용자는 아쉬운 출력과 한 줄의 의견만 주면 된다. 예: “좋은 결론 뒤에 같은 설명이 계속 붙는다.”

에이전트가 관련 지침을 확인하고, 문제와 연결되는 문장을 찾아 수정안을 만든다. 이미 있는 규칙으로 해결되는 문제라면 적용 누락이나 충돌부터 살핀다. 출력 사례가 없다면 현재 스킬로 대표 요청을 실행해 확인한다. 재현되지 않으면 무리하게 고치지 않는다.

### 2. 작게 고쳐 비교하기

한 번에 한 가지 행동만 바꾸고, 수정 전후에 같은 요청을 실행한다. 모델·설정·입력·대화 조건을 맞추고 두 버전은 별도 대화에서 실행한다.

첫 비교에는 다음 세 요청이면 충분하다.

- 문제가 드러난 요청 하나.
- 같은 능력이 필요한 새로운 주제의 요청 하나.
- 잘하던 능력을 확인할 요청 하나. 예: 비유로 개념을 쉽게 설명하면서 필요한 논리를 유지하는 글.

결과는 **덜 반복하는가 / 이해에 필요한 설명이 남았는가 / 요청과 의미·사실을 지켰는가**처럼 이번 문제에 맞는 쉬운 질문으로 살핀다. 대화·개요·대본·교육 스킬은 각 결과물에 맞게 질문을 바꾼다.

사용자에게 바뀐 부분을 나란히 보여주고, 잘하던 점이 유지됐는지도 설명한다. 전체 출력도 함께 보관한다. 중요한 설명이 빠지거나 새 사실 오류가 생기면 채택하지 않는다. 차이가 불분명하면 기존 버전을 유지한다. 이 소규모 비교로 일반적인 성능 향상을 입증했다고 말하지 않는다.

### 3. 좋아진 변경만 반영하기

사용자에게는 다음 정도로 보고한다.

> 문제: 결론 뒤에서 같은 내용을 다시 설명했습니다.  
> 변경: 기존 퇴고 규칙에서 중복 설명을 덜어내는 조건을 명확히 했습니다.  
> 비교: 전후 출력과 새 주제에서의 결과를 보여드립니다.  
> 판단: 무엇이 나아졌고 무엇이 불확실한지 설명합니다.

실제 확인 전에는 이 예시를 개선 결과로 보고하지 않는다. 반영이 승인된 범위라면 계속 적용하고, 계획·검토만 요청받았다면 수정안을 제시하는 것으로 마친다. 변경 전 버전과 전후 출력은 한 비교 기록에 남긴다.

## 첫 실행 순서

1. **optimizer 사용 절차부터 단순화한다.** 기본 지침을 위 세 단계로 바꾸고 조사 카드·점수 파일·명령어 입력을 사용자에게 요구하지 않는다. 기존 CLI는 기본 작업에서 호출하지 않는다.
2. **첫 실제 개선은 advisor의 질문 한 가지로 제한한다.** “글 하나 써줘”처럼 핵심 정보가 없는 요청에는 필요한 정보를 묻고, 주제와 목적이 주어진 요청에는 바로 진행하도록 하는 후보를 비교한다. 이미 맥락이 주어진 대화도 함께 확인한다.
3. **글 품질은 다음 회차에서 다룬다.** 반복 문제가 현재 출력에서도 나타날 때 `chaesajang-style`을 대상으로 비교한다. 일상 비유, 개념 간 연결, 논리적 전개, 절제된 결론을 유지한다.

계열 전체를 한꺼번에 줄이거나 합치지 않는다. 공통 코어를 바꾸게 되는 회차에는 그 규칙을 공유하는 스킬에서도 짧은 대표 요청을 확인한다. 개별 스킬 수정 때마다 계열 전체 평가를 반복할 필요는 없다.

실제 파일 변경은 `family.yaml`이 지정한 원본에서 한다. `skills/`, `dist/`, `.skill`은 생성물이므로 직접 고치지 않는다. 이 구분과 동기화는 에이전트가 처리하고 사용자에게는 변경 목적과 결과를 설명한다.

## Deep Research는 막힌 질문에만 사용한다

현재 지침과 전후 출력만으로 수정 방향이 분명하면 생략한다. “규칙이 이미 있는데 왜 계속 반복할까?”처럼 원인이 불명확할 때, 첨부한 [조사 프롬프트](../prompts/chaesajang-simple-deep-research.md)를 외부 도구에 넣는다.

이번 프롬프트는 **중복 설명을 줄이되 이해에 필요한 설명을 보존하는 방법**에 초점을 맞췄다. 조사 결과는 쉬운 한국어 제안 최대 3개와 출처로 받는다. 그중 하나만 다음 수정 후보로 사용한다. JSONL 변환, 전체 문헌 조사, 자동 채점 시스템 구축은 요구하지 않는다.

## 적용 기록 — 2026-09-09

**문제:** 작은 개선에도 6개 모드와 외부 증거·평가 산출물을 기본으로 요구해, 사용자가 무엇을 왜 하는지 파악하기 어려웠다. 이번 변경은 optimizer의 기본 사용 절차 하나에 집중했다.

**변경과 비교:**

| 변경 전 지침 | 변경 후 지침 |
|---|---|

**확인:** 스킬 형식 검사를 통과했다. 변경한 스킬·참조·사용 안내의 로컬 링크와 앵커 12개를 확인했다. `test_family_registry.py`, `test_research_prompt.py`, `test_cli_promotion.py`의 기존 테스트 79개가 통과했다. 이는 형식과 기존 기능의 검사이며 모델 출력 비교는 아니다.

**판단:** 작은 개선에 요구하는 절차를 줄인 문서 변경으로 반영했다. 실제 모델의 전후 행동이나 글 품질 향상은 아직 검증하지 않았다. advisor 질문 개선과 글 품질 후보는 이번 변경에 포함하지 않았다.
